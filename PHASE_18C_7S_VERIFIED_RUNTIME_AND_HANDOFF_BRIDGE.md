# Phase 18C.7S — Verified Runtime and Handoff Bridge Foundation

Continued on `codex/post-field-corrections-1` from `49ab849007f479d12209cf3e153949a9b19d9e63`, using Master Blueprint v1.1 and established security contracts without repeating earlier reviews. The previously documented absence of a standalone blueprint remains unchanged.

## Delivered guarantees

This milestone adds independently secure **native artifact verification and a native lease reservation**. It does not complete production Node identity or the 18C.7Q listener bridge, and grants no backend production authority. Both artifact and reservation objects explicitly report `ProductionAuthority == false`.

`BackendReleaseTrust` has a private constructor and no production key: `Production` is deliberately null. Only the explicitly isolated native self-tests create a fixture trust context from an ephemeral key held in native memory. A manifest cannot provide its own approval key, and there is no caller-key, verification, or launch CLI. Missing production trust rejects before any artifact ownership can be established. No current runtime hash, local build digest, path, unsigned manifest or self-reported identity is promoted into a production trust anchor.

`VerifiedBackendArtifacts` validates RSA-PSS/SHA-256 signatures against that trusted fixture context before interpreting the signed manifest. It clones input buffers before validation; rejects duplicate/extra fields, invalid roles/paths, duplicate paths (case insensitive), traversal, alternate streams, Windows device names, remote roots and observed reparse points; and enforces one runtime and one entrypoint. Signed lengths and SHA-256 measurements must match the retained open files. Files are held with read sharing only, preventing ordinary write/delete/replacement for the reservation lifetime, and are remeasured at use. Signature validation and hashes authenticate listed bytes relative to the supplied trusted fixture key, not the provenance of Node or the completeness of its execution graph.

Limits are a 64 KiB manifest, 256–512 byte signature with a 2048–4096 bit RSA key, 64 files, 128 MiB per file and 256 MiB total. Each signed release ID is consumed once per trusted policy object, including failed artifact checks, with 32 lifetime approvals per context. No approval is refreshed after replay or expiry. Pending/retained approval expires within ten seconds using both signed absolute expiry and elapsed time, with a native timer and synchronous rechecks. Cancellation and terminal failure publish revocation before observers and release file handles. External self-test failures are generic; internal classifications are only used for evidence assertions.

The existing native launcher lease still uses its private authenticated channel, same-image kernel peer checks and atomic Job ownership. The new association checks the exact live lease, its committed instance/receipt IDs, and its retained birth-specific process handle. `OwnedChild` now obtains the image path through `QueryFullProcessImageName` on that handle, rather than a PID lookup or child report. The image-path file must have the same kernel volume/file ID as the retained signature-approved runtime file, with measurements and owner liveness checked before and after. A correctly signed copy with identical bytes at another file object is rejected. Existing launch behavior is unchanged.

The resulting `NativeArtifactReservation` is one-use and retains the exact native lease/artifact objects. Artifact revocation ends the lease, and native owner/process/channel loss revokes the artifacts. Replay, wrong instance/receipt bindings, expired approval and terminated processes fail closed; replacement processes cannot revive the old objects. This is a **native-only association**, not a wire proof or a transferable 18C.7Q receipt. Invalid binding does not terminate an unrelated, previously unbound native lease.

## Exact remaining blockers and residual risks

1. **Production approval root and closed payload are absent.** The checkout has no pinned release-signing key, approved Node release/publisher policy, or signed manifest covering the backend entrypoint and its complete transitive executable dependency graph. The existing build digest is unsigned. This implementation deliberately accepts only isolated fixture approvals; its tests approve fixture bytes/native apphost files, not a production Node release.
2. **Measurement is not complete execution attestation.** Retained file sharing blocks ordinary mutation, but does not by itself prove which entrypoint/dependencies a child executed, stop injected in-process code or pre-existing writable mappings, or close every directory/namespace race between checking and a future launch. The kernel image-path/file-ID comparison is stronger than path/PID matching but is not a mapped-code attestation. No production path consumes it as sufficient evidence. Deployment needs controlled immutable payload/storage, a closed loading graph, controlled arguments and environment (including prevention of Node preload/module-path injection), and verified image/payload binding at atomic backend creation.
3. **The cross-process bridge to 18C.7Q is absent.** 18C.7R authenticates owned peers of the same native executable; it does not launch/verify Node. 18C.7Q holds exact Node-local owner, active receipt, listener and challenge references. The new reservation does not serialize those references, authenticate supplied GUIDs as 18C.7Q receipts, or identify an exact HTTP listener. A native bridge must establish bilateral verified backend provenance and map a private one-use native receipt to those exact objects without exposing challenge secrets to JavaScript. PID, port, paths, signatures over caller metadata, or stdout status cannot replace this mapping.

The actual production startup still launches Node/tsx through the existing script and supplies no trusted owner. The production HTTP/WS gate and 18C.7Q remain unchanged and default-deny/non-authorizing. No private challenge is copied into JS, browser state, URL, arguments, logs or error responses. Existing native TLS pinning, session protections, resource/field gates and camera safeguards are unchanged. Production activation must wait for complete end-to-end evidence; no temporary credential or trust bypass was introduced.

The smallest next scope is an approved signed release/payload workflow plus controlled native-owned backend loading/attestation. Only after that should a private native bridge attach the exact 18C.7Q receipt/listener and prove revocation across the complete lifetime.
