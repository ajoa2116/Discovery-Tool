# Phase 18C.1 — Isolated application session authority

Standalone module only: no imports from HTTP/WS routes, UI, native IPC or launcher. Production authentication behavior is unchanged. Nothing here supplies a public bootstrap endpoint or implements trusted delivery.

`ApplicationSessionAuthority` requires a synchronous trusted delivery interface and accepts an injected clock. `issueBootstrap` privately delivers a random 256-bit capability and returns nonsecret metadata only. Delivery failure invalidates the capability and hides exception details; redemption during delivery is refused. Capabilities expire after 30 seconds and are consumed once before session issuance. Redemption creates a separate random 256-bit session with a 15-minute absolute lifetime. Sessions can be independently revoked by their nonsecret ID; disposal irreversibly clears the authority. Invalid, foreign, expired and replayed tokens fail with a generic error.

Only SHA-256 token digests and metadata are stored in bounded, process-local maps (128 bootstraps and 128 sessions); expired entries are pruned on operations. No credentials, files, logs or network operations are involved. Secret wrappers redact ordinary JSON/string/inspection output; explicit `expose()` is reserved for private delivery and eventual authorized session transport. The clock must advance reliably; observed backward jumps cannot revive expired authority. There is no restart persistence or sliding renewal.

Trusted delivery is a requirement on the caller, not a security property established by dependency injection. Implementers must privately address the intended client, avoid public endpoints, URLs, persistent storage and logging, and complete delivery synchronously. No delivery implementation is provided here. Possession of a bearer secret grants authority until expiry/revocation: Origin/Host headers do not prove possession or process identity. This module does not defend against same-user process memory access, debugger/injection, executable replacement, stolen secrets or administrator compromise. A future launcher/bootstrap design must explicitly define those limits and any OS-backed process isolation; it must not claim that every local process is authenticated by this module.

Focused tests cover token shape/uniqueness, private issuance, rotation, replay/invalid/foreign rejection, exact expiry, clock rollback, independent revocation, disposal, failed/reentrant delivery, redaction, capacity and invalid clocks. No integration or camera/network tests are required for this isolated phase. Preserve existing native capability/pipe boundaries and the production native gate in later phases.
