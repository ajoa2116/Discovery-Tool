## Actual entry boundaries

- `src/server/index.ts` binds HTTP to `127.0.0.1:3001`. This limits direct remote access but does not authenticate browsers or local processes. Global `cors(...)` has no origin restriction. Outside `/api/camera-browser`, the mounted routers have no shared application authentication, Host allowlist, Origin validation or CSRF capability check. `taskHttpIntegration.middleware` observes tasks; it is not authorization.
- `/ws` uses `new WebSocketServer({ server, path: '/ws' })` without authenticated upgrade, Host/Origin validation or `verifyClient`. `broadcast` sends inventory/project/session and operational events to every connected client. No inbound WebSocket command handler exists in the inspected production server: the observed risk is unauthorized subscription/data exposure, not an implemented WS mutation API. Express middleware/CORS does not protect WebSocket upgrades.
- `/api/camera-browser` alone checks exact Host (`localhost:3001` or `127.0.0.1:3001`), exact HTTP Origin (same endpoints; port 5173 additionally permitted when `NODE_ENV !== 'production'`) and `X-CCTV-Workspace: 1`. It rejects missing values, uses a 2 KB JSON parser, no-store responses, restricted bodies and generic errors. These are browser-origin controls, not local-process authentication: a local caller can supply these headers. Global permissive CORS does not bypass this router's independent checks.

## Controls already present and their limits

- Backend camera workflows require saved credential material, preview/plan IDs and explicit confirmation, with device/collision checks, capability/value validation, cancellation rules, verification and audits. Pair checks current physical adapter identity/baselines, candidate safety and recovery state. These checks differ by service; they are not a universal current-evidence policy. In particular, camera network `apply` retrieves a stored preview and rechecks the device, but has no explicit preview-age expiry check. Do not infer that a plan ID or `confirmed: true` proves a trusted technician request.
- `CameraBrowserSessions` applies Phase 6 access decisions and binds leases to device ID, anchor, project context, address and exact origin. It uses random 256-bit secrets, stored hashes/timing-safe comparison, 30-second one-time native handoff, rotated channel token, five-minute active expiry, reconciliation and irreversible revocation. Workspace tokens cannot redeem native handoffs or authorize broader APIs.
- `CameraRendererService` receives no controlled-fixture authority in production composition. Native launch requires that in-process authority; no request field, preference or environment flag grants it. Capability probing uses the fixed host path, no shell, restricted environment and bounded output/time; it does not navigate a camera.
- Native IPC (`native_camera_proof.ts`, `Program.cs`, `WindowsBoundary.cs`, `Wire.cs`) has no HTTP redemption endpoint or native network listener. Private redirected streams feed protected named pipes: current-logon SID DACL, non-inherited handles, random names, first-instance/remote-client rejection, kernel peer PID/session/image checks, owned kill-on-close Job Object, strict framed protocol, deadlines and heartbeat reauthorization. Broker/host reject elevated, session-0 and noninteractive execution. These controls do not defeat account compromise, process injection, administrators or replacement of the development executable.
- `CameraWindow.cs` confines navigation to the granted origin, cancels certificate errors, denies popups/downloads/permissions and exposes no general script/host bridge. Separate InPrivate environments and bounded owned-profile cleanup exist. `WebResourceRequested` coverage has not proven isolation of every worker, WebSocket or browser-internal channel; cleanup after crashes is not guaranteed secure deletion.
- Vault-safe DTOs, secret redaction and selected generic error paths reduce disclosure. Some broader handlers still return `error.message`; no uniform safe-error or response-cache policy is established across the API.

## Smallest safe implementation order

1. **Define and implement trusted application bootstrap first.** Specify supported production/dev origins, trusted launcher/session delivery, session lifetime/revocation and local-process threat assumptions. Do not expose a reusable authority through an unauthenticated localhost bootstrap endpoint. A header marker, Origin check or secret downloadable by every local caller is insufficient for local-process authentication; stronger same-user process isolation may require an OS broker/privilege split.
2. **Install one fail-closed HTTP boundary before parsers, snapshot/task middleware and every API router.** Validate exact Host and allowed Origin, restrict CORS, require the trusted application session for reads and writes, enforce CSRF protection and input/resource bounds. Explicitly define missing-Origin behavior for authorized non-browser clients. Cover camera/adapter writes, vault, project file writes, discovery and support operations without bypasses; preserve existing domain safety checks and the native production gate.
3. **Protect `/ws` upgrades with the same trust model.** Validate Host/Origin and application session before subscribing, bound connections, revoke disconnected/expired authority and minimize event payloads. Do not introduce credentials in URL query strings or add inbound controls as part of this fix.
4. **Bind workflow plans and sensitive operations to the authenticated session.** Add expiry/replay/current-evidence checks where absent, review project-save paths, credential associations, cancellation ownership and consistent safe responses. Validate denial of missing/forged authority, hostile/null origins, rebinding Hosts, foreign/expired plans and unauthorized WS clients using isolated mocks/fixtures before any physical operation.
5. **Complete native exposure prerequisites separately.** Prove resource isolation against privileged localhost authority across workers/WS/internal channels; define profile crash retention; validate unelevated launch for elevated applications; protect/sign installation and updates. Keep TLS rejection and existing native checks. Only after reviewed implementation and adversarial validation explicitly reconsider production composition/gate removal. Phase 17F compatibility/certificate UX remains separate.
