# Isolated backend staging

`node scripts/stage-backend.cjs --out NEW_EXTERNAL_DIRECTORY [--root CHECKOUT] [--entry RELATIVE_PATH ...]`

The default explicit backend root is `src/server/index.ts`. Custom roots replace it. Output must be a fresh directory outside the checkout; existing stages are never overwritten. The tool emits JavaScript with the source layout preserved and relative TypeScript import extensions rewritten. It performs transpilation, not type checking, bundling or runtime verification. The compiler is a build input, not a production runtime approval.

Dependency candidates come from observed runtime-reference ancestry and the installed lockfile graph (including nested/optional/peer candidates). Whole inventoried package membership is copied with recorded reasons; that does not prove every member is required or that all files were inventoried. Missing, computed, conditional and unknown inputs remain unresolved. Unknown/type-only candidates are listed, not silently treated as excluded. No automatic TSX/esbuild necessity or removal claim is made.

Selected-package dependency edges are classified as `required`, `optional-with-observed-fallback`, or `unresolved`. Required means matching lockfile/package declarations with a lock candidate, not verified loading. Optional fallback status requires matching optional declarations and a narrow static observation for WS peers `bufferutil` and `utf-8-validate`: existing function exports precede a literal require inside a try with an empty catch. Evidence includes metadata sources, declared ranges, optional peer metadata, versions, lock integrity text and fallback source/line/guard/default-export locations. Integrity text is recorded, not checked. No discovered dependency is executed. Missing lock resolutions and original inventory flags remain unresolved even when an optional fallback is observed; static observations establish neither safety nor complete closure.

`loadingSummary` separates unresolved records affecting selected/observed paths and package edges from unselected inventory records, with counts, causes and records. Other inventory issues remain a separate group. Missing required edges and failed outputs are highlighted. These are review priorities, not proof that unknown candidates are excluded or that selected paths load successfully. Runtime compatibility, conditional loading, native hosts and helper resolution still need later verification.

Observed module-relative file/directory assets retain their layout. Native-host neighboring files are copied as candidates, with native loading closure explicitly unresolved. PowerShell scripts are copied only when selected by observed references; OS executable search and inline/generated helper commands remain unresolved. UI `dist` assets are copied if an observed module URL selects them. No UI build, dependency installation, runtime download, backend/helper execution or physical operation occurs.

Output includes `stage-manifest.json`, the complete original annotated `inventory.json`, and minimal ESM `package.json` metadata without startup scripts. Records identify selection reasons and successful copies/transpilation or failures. Every output is non-authorizing; production authority, complete closure and runtime validation remain false. There is no packaged Node runtime, signing policy, launcher or production integration.

Inventory bounds remain applicable; asset expansion and copying additionally enforce a 20,000 selected-file limit, 128 MiB per file and 256 MiB total source bytes. Symlinks/junctions are rejected or explicitly flagged. Copy/transpilation errors leave a partial stage and are recorded; failed stages are not automatically deleted. Source mutation races, generated-code loading, native dependencies and compiler/runtime compatibility remain unverified.

Focused builder tests only: `node --import tsx --test src/test/backend_staging.test.ts`.

## Selected dependency resolution in the isolated probe

The existing selected-path capture also exposes fixture-only `retain`, `simulateUse` and `dispose`. Retention uses the same exact selection/reference/path checks, opens a read handle, compares its metadata identity to the mapped file and records a bounded SHA-256 measurement. It rechecks identity around measurement. At inert simulated use, it revalidates the selected path and compares both a newly opened intended file and the retained handle against the original identity and digest. Same-size changed bytes can therefore be denied even when file identity, length and modification time are restored. A different file object with identical bytes is also denied. Missing, redirected, ambiguous or unselected paths fail before an inert success result. Evidence is process-local and one-use; denial, success or disposal permanently ends that evidence and attempts descriptor cleanup. Failed closure is retained as pending cleanup, never reported as closed. No consumer callback or executable operation is accepted.

Descriptor ownership is registered immediately after successful open, including partial validations that never publish evidence and secondary simulated-use handles. Evidence becomes terminal before cleanup; disposal invalidates all evidence before closing resources and continues across errors. Close failures preserve the primary operation reason and separate cleanup codes. A bounded second close attempt occurs only after an open-descriptor probe (with known file identity checked when available); `EBADF` after a thrown close confirms closure without blindly closing that number again. Transient pre-close and post-close errors are exercised. Unknown or persistently rejected closure stays tracked in `cleanupState()`/`cleanupJournal`, denies new retention and can be released by subsequent disposal after the injected fault is removed. Disposed capture objects cannot issue new evidence. Persistent OS refusal cannot be turned into a closure guarantee.

Cleanup tests inject opening, identity, digest-read, secondary-open/read, final verification, pre/post-close and disposal failures. They independently track acquired descriptors and confirm actual closure using the original `fstatSync` returning `EBADF`, not just terminal flags. Sixteen repeated validation/read/cleanup failures leave no acquired descriptors alive; checked private-file rename and final deletion remain possible. Normal disposal, multi-file disposal, orphaned partial-validation resources, uncertain close-state recovery and primary-failure preservation are covered. These trusted synchronous fixture observations do not establish safety under arbitrary concurrent descriptor reuse or production execution races.

These optional checks read only explicitly selected fixture-controlled test bytes; the prior mapping-only probe remains metadata/call capture and does not automatically hash real helper/native files. Retention evidence and outcomes are separate from metadata capture records and package admission. Bounds reuse the existing 64 retained files / 128 MiB per file / 256 MiB active total ceilings; no native manifest limit changes. Tests construct only synthetic helper/asset bytes in private temporary stages, preserving selection/reference shapes. No inventory, runtime/provider discovery or actual helper execution occurs.

Focused checks: `node --test --test-concurrency=1 --test-name-pattern="retained files|helper mapping|package admission|exact package hooks" src/test/retained_staged_files.test.cjs src/test/staged_backend_loading.test.cjs`. Cases cover unchanged helper/assets, encoded/native Windows paths, same-size mutation with restored metadata, replacement by different or identical bytes, deletion, ambiguous/unselected selections, wrong/outside paths, disposal/replay and supported directory junction/symlink redirection. On the observed Windows host, the retained handle allowed ordinary file replacement/deletion but blocked renaming its containing directory; moving the file and substituting the now-empty directory with a junction exercised actual redirection denial. That observation is not a general Windows sharing guarantee. Unsupported link creation is explicitly reported rather than counted as redirection verification.

`raceFree:false` remains explicit. Standard Node read handles are not demonstrated deny-write/delete locks; metadata and digest observations are sequential, not atomic execution authorization. Concurrent mutation during or after measurement, replacement after the final check, mapped-code integrity, hostile filesystem providers, protected ancestor/installation guarantees and production TOCTOU protection remain unresolved. The retention descriptor is not passed to a real loader/process. Signing, production launch and provider execution remain outside this fixture.

`--mapping-only` uses the same prepared-stage probe and exact package admission, with narrowly scoped substitutions at `execFile`, `spawn`, `readFileSync`, `existsSync` and `express.static`. `runStagedProbe(..., { mappingOnly: true })` selects this mode without inventory regeneration. Only emitted Windows receive observation, native capability request, build identity reads and UI asset construction are exercised. Original process/file functions are never forwarded: subprocess capture stops or returns synthetic JSON, metadata reads return synthetic JSON, and static middleware is inert. The constructed root handler is called directly; Express router completion scheduling remains blocked.

Capture requires one matching existing module-URL reference and one successful exact file selection with its original URL-selection reason. Converted file URLs/paths must match the intended relative file within the canonical stage. Nonlocal URLs, queries/fragments, drive-relative/device/ADS paths, explicit traversal, wrong targets, duplicate/missing/unresolved selections, links and missing files deny capture. Selected files receive metadata checks only (device/file identity, size, modification time), with identity stability on repeated captures. No file contents or sensitive files are read by capture; build/package values are synthetic. A selected directory URL is checked through each explicitly selected child file, never admitted as a directory. Windows conversion and encoded filename cases have focused tests.

`helperMapping` records boundary requests/arguments, exact file mappings, original selection reasons, metadata identity and selected-reference coverage separately from module loads. Static-child records are selection checks made during captured middleware construction, not browser file requests. All records remain `capturedOnly`, `executed:false`, `contentsRead:false`; unresolved inventory records remain unchanged. URL objects may already have undergone URL normalization; matching the final path plus the original selected reference is the fixture claim. This is not hash/signature verification, retained-handle/race-free attestation, actual helper execution, native/provider compatibility or asset runtime verification. Current synthetic work does not authorize installation, production requests or camera operations.

`--resolution-only` selects a bounded mode of the existing `.loading-probe.cjs`. The exported `runStagedProbe(stage, manifest, testOnlyFixtures, { resolutionOnly: true })` runs an already prepared **fresh external fixture copy**, containing the original staging/inventory evidence and current probe/review controls. Preserve the original stage and prior reports; the result writer refuses to overwrite an existing `loading-report.json`. This mode does not call the inventory or staging builder, and skips application/provider lifecycle checks.

The mode resolves exact admitted files without executing their bodies, then resolves declared package edges using literal specifiers from the existing `inventory.json` whose importing files are themselves admitted. Package-root names are not invented: packages such as `dunder-proto` and `math-intrinsics` export subpaths only. Nested package ownership and type-only/unreviewed importers are retained separately. Resolution uses current Node `require` conditions; reference kinds and lines remain evidence, not proof of branch execution. No new target is admitted by resolution. The existing four synthetic package imports also exercise default Node ESM/CommonJS interoperation. The reviewed `ws/index.js` require export is admitted individually alongside its existing ESM wrapper and reviewed lib files.

`dependencyResolution` distinguishes resolved/admitted paths, missing/ambiguous requests, conditional/unexercised paths and external-execution dependencies. Original selection reasons, unresolved records, optional fallback evidence, presence checks and observed loads remain separate. Unreviewed browser/encoding alternatives and absent peers remain denied. Native host/CLR/DLL files and the selected PowerShell script receive presence evidence only; neither is executed. Browser assets and computed/runtime loading alternatives remain unexercised. `sql.js`/WASM inventory candidates are not selected by this backend stage; their absence is not a verified exclusion from future execution closure. Passing resolution is non-authorizing and does not establish provenance, byte integrity, complete conditional behavior or provider compatibility.

Focused loading harness: `node --test src/test/staged_backend_loading.test.cjs`, or `node scripts/staged-backend-loading.cjs NEW_EXTERNAL_STAGE_DIRECTORY`. This generates a fresh stage and launches only its isolated probe through the specified Node executable (default: the harness's `process.execPath`). The isolated probe now admits package modules at file level. `staged-backend-review.cjs` contains exact reviewed Node synthetic paths, not package/directory patterns. `buildPackageAdmission` intersects those paths with unique successful `copied-candidate` records whose source/output and selection reasons are present and unambiguous. Missing, failed, unresolved file selections, case aliases and duplicate review/selection records deny admission. Package membership alone is insufficient. `.loading-package-admission.json` and `loading-report.json.packageAdmission` preserve admitted/denied paths, staging reasons, review reasons and the original unresolved records; the child rebuilds admission from its staging manifest and fixed review rather than trusting that output JSON as an allowlist. Runtime `loadedModules` remains separate observation and never expands admission.

Synchronous Node resolve/load hooks reject unlisted package files before ESM or CommonJS bodies execute, including transitive imports/requires. The existing project-module and operation guards remain active. Browser alternatives, lazy iconv encoding tables, optional WS native peers and computed view engines are not implicitly admitted. Reference-analysis gaps in successfully copied files remain unresolved edge evidence; they cannot select additional targets. Resolution metadata read internally by Node, generated code, ordinary filesystem asset reads, mutable-file races and native/provider loading are not made secure or complete by these hooks. Admission remains fixture-only, non-authorizing and not a production sandbox, integrity verification or dependency-closure claim. The integrated native driver and production startup do not consume this mechanism.

The probe gets a minimal environment without preload/module-search variables, no TSX/esbuild, no TypeScript stripping, no addons, and Node permissions restricted to reading the stage (no subprocesses, workers or filesystem writes). Synchronous resolution hooks reject paths outside the stage, TS/TSX/native addon inputs, TSX/esbuild and project modules outside the reviewed allowlist. In-probe guards reject network/socket creation, adapter enumeration, subprocess calls and timers before imports. Focused negative checks exercise those guards and entrypoint/package rejection. These controls are an experiment boundary, not a production sandbox or verified dependency closure. The report records exact Node executable/version/arguments, loaded files, failures, blocked attempts and unexercised selected outputs. Node 24 results do not approve its production use; existing readiness policy still requires separate approved runtime validation. Partial stages/reports are retained for inspection, and the original manifest remains non-authorizing and runtime-unvalidated.
