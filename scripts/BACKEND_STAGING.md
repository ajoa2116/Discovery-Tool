# Isolated backend staging

`node scripts/stage-backend.cjs --out NEW_EXTERNAL_DIRECTORY [--root CHECKOUT] [--entry RELATIVE_PATH ...]`

The default explicit backend root is `src/server/index.ts`. Custom roots replace it. Output must be a fresh directory outside the checkout; existing stages are never overwritten. The tool emits JavaScript with the source layout preserved and relative TypeScript import extensions rewritten. It performs transpilation, not type checking, bundling or runtime verification. The compiler is a build input, not a production runtime approval.

Dependency candidates come from observed runtime-reference ancestry and the installed lockfile graph (including nested/optional/peer candidates). Whole inventoried package membership is copied with recorded reasons; that does not prove every member is required or that all files were inventoried. Missing, computed, conditional and unknown inputs remain unresolved. Unknown/type-only candidates are listed, not silently treated as excluded. No automatic TSX/esbuild necessity or removal claim is made.

Selected-package dependency edges are classified as `required`, `optional-with-observed-fallback`, or `unresolved`. Required means matching lockfile/package declarations with a lock candidate, not verified loading. Optional fallback status requires matching optional declarations and a narrow static observation for WS peers `bufferutil` and `utf-8-validate`: existing function exports precede a literal require inside a try with an empty catch. Evidence includes metadata sources, declared ranges, optional peer metadata, versions, lock integrity text and fallback source/line/guard/default-export locations. Integrity text is recorded, not checked. No discovered dependency is executed. Missing lock resolutions and original inventory flags remain unresolved even when an optional fallback is observed; static observations establish neither safety nor complete closure.

`loadingSummary` separates unresolved records affecting selected/observed paths and package edges from unselected inventory records, with counts, causes and records. Other inventory issues remain a separate group. Missing required edges and failed outputs are highlighted. These are review priorities, not proof that unknown candidates are excluded or that selected paths load successfully. Runtime compatibility, conditional loading, native hosts and helper resolution still need later verification.

Observed module-relative file/directory assets retain their layout. Native-host neighboring files are copied as candidates, with native loading closure explicitly unresolved. PowerShell scripts are copied only when selected by observed references; OS executable search and inline/generated helper commands remain unresolved. UI `dist` assets are copied if an observed module URL selects them. No UI build, dependency installation, runtime download, backend/helper execution or physical operation occurs.

Output includes `stage-manifest.json`, the complete original annotated `inventory.json`, and minimal ESM `package.json` metadata without startup scripts. Records identify selection reasons and successful copies/transpilation or failures. Every output is non-authorizing; production authority, complete closure and runtime validation remain false. There is no packaged Node runtime, signing policy, launcher or production integration.

Inventory bounds remain applicable; asset expansion and copying additionally enforce a 20,000 selected-file limit, 128 MiB per file and 256 MiB total source bytes. Symlinks/junctions are rejected or explicitly flagged. Copy/transpilation errors leave a partial stage and are recorded; failed stages are not automatically deleted. Source mutation races, generated-code loading, native dependencies and compiler/runtime compatibility remain unverified.

Focused builder tests only: `node --import tsx --test src/test/backend_staging.test.ts`.

`scripts/staged-fixture-entrypoint.cjs` is a non-production entry copied as `node-launch-entry.cjs` by the integrated owned-Node fixture. Direct CLI invocation always denies before application loading. Its module function requires the measured native addon to authenticate the inherited owner handle and protected pipe before importing the staged synthetic HTTPS/WS composition. The existing fixture manifest measures this entry as its ninth Node/control input; the 64-file ceiling is unchanged. It never selects production providers or creates production receipts. Ordinary `start-production.cjs` remains unchanged and still uses TSX. Guarded module resolution, owner-selected endpoint pin verification and terminal cleanup remain mandatory fixture controls.

`fixture-runtime-preflight.cjs` runs in the integrated test's orchestration before native launch, without widening the child filesystem permissions. It checks the fixed fixture Node image, staged controls/addon, build-recorded owner bytes/paths, composition selection, owner runtime metadata and bounded local .NET framework candidates. Its report is informational (`authenticated:false`, `productionAuthority:false`, `completeClosure:false`); native signed fixture verification and live authentication remain mandatory. Framework presence is not host selection or provider verification. External WebView2, computed imports, DLL resolution and production deployment policy remain unresolved. It adds no child payload file or production entrypoint. Focused checks: `node --test src/test/fixture_runtime_preflight.test.cjs src/test/staged_fixture_entrypoint.test.cjs`.

Focused loading harness: `node --test src/test/staged_backend_loading.test.cjs`, or `node scripts/staged-backend-loading.cjs NEW_EXTERNAL_STAGE_DIRECTORY`. This generates a fresh stage and launches only its isolated probe through the specified Node executable (default: the harness's `process.execPath`). It never imports the real entrypoint: that file starts listeners/timers, pair recovery and credential initialization on import. Selected route/task/foreground/vault/authentication modules are exercised with synthetic requests, synthetic discovery and an in-memory credential store. Express/CORS/WS/XML parsing packages load; no real API/WS listener or discovery transport is constructed.

The probe gets a minimal environment without preload/module-search variables, no TSX/esbuild, no TypeScript stripping, no addons, and Node permissions restricted to reading the stage (no subprocesses, workers or filesystem writes). Synchronous resolution hooks reject paths outside the stage, TS/TSX/native addon inputs, TSX/esbuild and project modules outside the reviewed allowlist. In-probe guards reject network/socket creation, adapter enumeration, subprocess calls and timers before imports. Focused negative checks exercise those guards and entrypoint/package rejection. These controls are an experiment boundary, not a production sandbox or verified dependency closure. The report records exact Node executable/version/arguments, loaded files, failures, blocked attempts and unexercised selected outputs. Node 24 results do not approve its production use; existing readiness policy still requires separate approved runtime validation. Partial stages/reports are retained for inspection, and the original manifest remains non-authorizing and runtime-unvalidated.

The expanded explicit review list is `staged-backend-review.cjs`. Project/report state, readiness, adapter and diagnostic definitions and server routes are imported without calling operational providers. Extra behavioral checks use empty project/report state, synthetic adapter/matrix services and a negative camera-access decision. OS credential initialization is blocked in the child. `coverageClassification` retains every selected JavaScript output with original selection reasons and static entrypoint evidence, baseline loading status, priority, load observation and exclusion reason. No exclusive test/build/browser role is inferred from a filename or installed-package status. Unknown records and stage unresolved flags remain; imports establish neither successful operational behavior nor closure.

`backend_application.ts` now exports import-safe construction and explicit startup/shutdown. The production launcher supplies only existing defaults and remains excluded from the probe. The harness separately transpiles exactly `src/test/backend_lifecycle_fixture.ts`, which the inventory intentionally excludes, and records it in `test-fixture-manifest.json` and `testOnlyFixtures`; the production staging manifest is unchanged. This test-only input exercises emitted composition startup, fixed HTTP/WS denial, host validation, partial-start failure cleanup, cancellation and late callbacks using synthetic listener/monitor/initialization dependencies. The real initialization methods and all OS/helper/native operations remain blocked. `startupBlockers` now identifies remaining default-provider/runtime/native ownership verification rather than absence of a composition boundary. No environment flag selects these fixtures in production.
